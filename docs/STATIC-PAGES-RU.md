# Статическая генерация страниц Thinking People

Система собирает готовые HTML-страницы для доступных адресов и языков подключённых шаблонов. Главная включена в общую генерацию: `/en/` и `/lv/` используют глобальный вариант языка Plasmic и предварительную загрузку существующих запросов. Язык определяется адресом: `/en/...` или `/lv/...`. Данные Strapi и глобальный языковой вариант Plasmic выбираются во время сборки, поэтому посетителю не требуется ждать загрузки текста из CMS.

Сохраняется режим Next.js `output: "standalone"`. Сервер Next.js обслуживает готовые страницы, формы, revalidate и обработку изображений. Это не экспорт сайта в папку `out`.

## Как запустить сборку

На сервере под пользователем `bsadmin`:

```bash
tp-site
```

Из root-сессии:

```bash
sudo -iu bsadmin tp-site
```

Команда получает изменения из GitHub, создаёт отдельный релиз, собирает сайт, проверяет результат и переключает работающий процесс. При незакоммиченных изменениях в исходниках обычная команда останавливается. Для намеренной сборки таких изменений предусмотрено:

```bash
tp-site --local
```

Сначала сохраняйте правки в Git. Не используйте `--local` как постоянную замену синхронизации с репозиторием.

Если сборка или проверка HTML завершилась ошибкой, новый релиз не включается. Кэш изображений остаётся общим для релизов.

## Какие страницы попадают в сборку

Список шаблонов берётся из `plasmic.json`: используются синхронизированные компоненты с типом `page`. Обычные компоненты, черновики без синхронизации и отдельные записи CMS без шаблона страницы не превращаются в страницы автоматически.

| Адрес | Источник |
| --- | --- |
| `/[locale]/` | Главная: глобальный вариант языка + существующие запросы Strapi |
| `/[locale]/cases/` | Страница каталога из Plasmic |
| `/[locale]/cases/[slug]/` | Опубликованные записи `caseStudies` |
| `/[locale]/learning/[slug]/` | Опубликованные записи `directions` |
| `/[locale]/experts/` | Страница каталога из Plasmic |
| `/[locale]/experts/[slug]/` | Опубликованные `experts` с `hasProfilePage = true` |
| `/[locale]/diagnostics/` | Страница Plasmic |
| `/[locale]/events/leadership-on-trial/` | Фиксированная страница мероприятия из Plasmic |
| `/[locale]/leadership-on-trial/` | Сохранённый исходный адрес мероприятия из Plasmic |

`showInDirectory` управляет попаданием эксперта в каталог через существующий запрос. `hasProfilePage` управляет созданием его персонального адреса. Поэтому Elena Barisone может присутствовать в каталоге без отдельной страницы.

Для будущего шаблона `/[locale]/blog/[slug]/` уже предусмотрено соответствие коллекции `articles`. Пока такого синхронизированного шаблона нет, статьи не создают страницы блога.

Для подключённых CMS-страниц список slug получается отдельно для каждого языка с пагинацией. Совпадение slug у переводов не означает, что перевод опубликован. Отсутствующая локализация не подменяется английской.

## Как выбирается язык

Базовый язык указан в `config/static-pages.json`: `en`. Дополнительные языки читаются из сгенерированного провайдера `PlasmicGlobalVariant__Language.tsx`. Сейчас это `lv`.

Это список языков, поддерживаемых интерфейсом сайта. Само добавление локали в админке Strapi ещё не добавляет её в сайт: нужно также подготовить соответствующий языковой вариант Plasmic.

Для EN провайдер получает базовый вариант (`undefined`); для LV — `lv`. Сопоставление применяется и во время предварительной загрузки запросов, и при обычном рендеринге.

Параметры `locale` и `slug` передаются из `getStaticProps`. Для совместимости с существующим дизайном параметр `local` также содержит текущую локаль. Файл диагностики с `[local]` приводится к маршруту с `[locale]`, чтобы Next.js не получал конфликтующие имена одного сегмента.

Если текст в Plasmic не переведён в варианте LV, он останется базовым. Сборка не переводит текст автоматически. Если нужного CMS-перевода нет, его персональная страница вообще не создаётся.

## Как работают запросы Plasmic

Обёртка запускает `extractPlasmicQueryData` с нужными параметрами и провайдерами. Полученный кэш передаётся в `PlasmicQueryDataProvider`. Затем Next.js создаёт HTML с результатом существующего запроса.

Запросы, их параметры, заголовки и авторизация внутри сгенерированных компонентов не переписываются. Новые служебные запросы сборки только перечисляют опубликованные записи и проверяют наличие локализаций.

Для служебных запросов используются `STRAPI_GRAPHQL_URL` и `STRAPI_BEARER_TOKEN` из закрытого файла `/home/bsadmin/shared/tp-site/app.env`. Токен не включается в manifest или документацию. Не добавляйте этот env-файл в Git.

Если новый запрос страницы жёстко использует `en`, одна обёртка не сделает его многоязычным. Требуется согласованная настройка запроса на параметры страницы. По правилам проекта существующий fetch нельзя менять без явного подтверждения пользователя.

## Как добавить контент или перевод

1. Создайте запись в соответствующей коллекции Strapi.
2. Укажите slug. Для переводов используйте тот же slug.
3. Создайте перевод через локализацию той же записи.
4. Опубликуйте каждую нужную локаль отдельно.
5. Запустите `tp-site`.

Для нового slug или новой локализации нужен новый билд: маршруты работают с `fallback: false`. Неизвестные адреса возвращают 404 и не создаются при первом посещении.

Для обновления текста существующей страницы можно использовать текущий API revalidate с конкретным локализованным URL. Revalidate не перечитывает список доступных адресов и не заменяет билд при добавлении или удалении страниц. При снятии публикации надёжный способ обновить сайт и sitemap — новый билд.

## Как добавить страницу Plasmic

Создайте страницу с локализованным маршрутом, например `/[locale]/about`. Синхронизируйте проект Plasmic в GitHub и выполните `tp-site`. Для страницы без дополнительных параметров обёртка создаст адреса для всех поддерживаемых языков.

Для страницы с `[slug]` укажите соответствие маршрута и коллекции в `collectionsByRoute` файла `config/static-pages.json`. Например:

```json
"/[locale]/blog/[slug]": "articles"
```

Сама страница должна содержать настроенный запрос и привязки отображения данных. Соответствие в конфигурации определяет список адресов, а не заменяет запрос страницы.

Для Single Type, которому не нужен slug, предусмотрено `singleTypesByRoute`. Сейчас этот список пуст: главная генерируется для всех языков глобального варианта, без требования опубликованной записи homepage в каждой локали Strapi. Существующие запросы получают локаль из адреса; генератор их не изменяет. Исключения задаются по ID компонента в `unmanagedPages`; его готовые адреса добавляются в sitemap, но обёртка не перезаписывается. Для ограничений публикации отдельных коллекций предусмотрено `collectionFilters`.

Незнакомый динамический параметр или `[slug]` без источника приводит к понятной ошибке сборки. Система не придумывает произвольные адреса.

Обёртки, отмеченные `Managed by scripts/prepare-static-pages.mjs`, создаются автоматически. Общую логику меняйте в `LocalizedPage` и `localized-static-pages`, а оформление — в Plasmic. Ручные изменения этих обёрток будут перезаписаны при следующей подготовке.

## Как добавить язык

1. Добавьте локаль в Strapi.
2. Добавьте вариант с тем же кодом в глобальную группу Language в Plasmic.
3. Переведите меню, кнопки и статический текст в этом варианте.
4. Опубликуйте переводы нужных записей Strapi.
5. Синхронизируйте Plasmic и запустите `tp-site`.

После синхронизации новый код попадёт в сгенерированный тип `LanguageValue`, откуда сборщик прочитает его автоматически. Названия вариантов должны быть кодами локалей: `lv`, `de`, `fr`, а не словами `Latvian` или `German`.

## Переключатель языка

Переключатель должен вести на другой URL. При одинаковом slug меняется только сегмент языка, но ссылку следует показывать лишь для опубликованной версии.

Обёртка формирует `languageLinks` в props страницы: список доступных переводов с полями `locale` и `url`. Эти данные используются для тегов `hreflang`; их также можно подключить к интерфейсу переключателя отдельной доработкой.

Сам интерфейс переключателя в рамках настройки генерации не меняется. Простое переключение Global Variant по клику без смены адреса не заменяет переход между языковыми страницами.

## Sitemap и проверки

Sitemap `/sitemap.xml` использует список URL текущего билда. Он не ссылается на отсутствующие шаблоны и непубликованные переводы. Базовый домен для ссылок задаёт `SITE_URL`.

Список ожидаемых адресов хранится в `.tp-generated/static-pages.json`. После сборки создаётся `.tp-generated/build-report.json` с результатами проверки. Эти файлы относятся к конкретному релизу и не редактируются вручную.

Проверка сопоставляет ожидаемые URL с `prerender-manifest.json`, проверяет наличие HTML и соответствующий атрибут `lang`, а также наличие основного текста CMS в HTML вне скриптов. Главная входит в проверки HTML, локали и статических маршрутов. Для CMS-страниц предварительная загрузка должна содержать данные нужной коллекции или Single Type; пустая выдача останавливает сборку.

Команды для разработчика из каталога проекта:

```bash
npm run build
node scripts/verify-static-build.mjs
```

Первую команду выполняйте в рабочей копии для разработки или в отдельном релизе. Для обновления работающего сервера используйте `tp-site`.

## Основные файлы

- `config/static-pages.json` — базовый язык и источники динамических адресов.
- `scripts/prepare-static-pages.mjs` — обнаружение страниц, перечисление локализаций и создание обёрток.
- `components/LocalizedPage.tsx` — одинаковые контексты языка и данных для сборки и браузера.
- `lib/localized-static-pages.tsx` — `getStaticPaths`, `getStaticProps`, предварительная загрузка запросов.
- `scripts/verify-static-build.mjs` — проверка готовых HTML-файлов.
- `pages/_document.tsx` — язык HTML-документа.
- `pages/sitemap.xml.tsx` — sitemap текущего билда.

Navbar сохраняет `position: fixed`; компенсирующий `padding-top: 80px` остаётся на корневом элементе страницы в дизайне. Каталоги сохраняют AnimatedFilterGrid с `layout: masonry`.

## Google Analytics / Google Tag Manager

Контейнер `GTM-TJTRVDJM` установлен в `pages/_document.tsx`: стандартный bootstrap в `<head>` и noscript iframe в начале `<body>`. Он загружается один раз на документ для всех локалей; `/plasmic-host` исключён.

На 18.11.2026 опубликованный контейнер направляет данные в GA4 `G-BHN4JNPDCH` и содержит автоматический учёт просмотров при изменении History API. Поэтому переходы Next.js учитываются контейнером; ручной `gtag('event', 'page_view')` или дополнительный History Change-триггер добавлять параллельно не нужно — возможны дубли. При изменении контейнера проверяйте первоначальный просмотр, переход через Next Link, Назад/Вперёд в Tag Assistant / GA4 DebugView.
